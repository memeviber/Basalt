# Bootstrap Basalt Function Reference

## Scope and reading guide

This document describes the control-plane functions of the Bootstrap Basalt compiler. It is intentionally organized around the compiler’s major phases: parsing, type and ownership checking, C emission, deferred cleanup, and recursive source expansion. The companion diagram is [`bootstrap-function-graph.mmd`](./bootstrap-function-graph.mmd), with a rendered image at [`bootstrap-function-graph.png`](./bootstrap-function-graph.png).

The graph is a **selected function-level view**, not a complete inventory of every helper in `src/bootstrap/basaltc.basalt`. It shows the functions that determine syntax construction, semantic validation, control-flow joins, generated-C structure, defer cleanup, and recursive include behavior. Edges represent direct calls between selected functions. Calls to lower-level helpers are grouped as external boundaries so that the diagram remains readable. The source of record is the Bootstrap compiler at [`src/bootstrap/basaltc.basalt`](../../src/bootstrap/basaltc.basalt) [1].

> **Interpretation rule:** an arrow `A → B` means that `A` directly invokes `B` in the selected source slice. The “Key callers” and “Key callees” columns use the same selected-slice convention; they are not claims that no other helper calls exist.

## Pipeline overview

The Bootstrap compiler follows a staged pipeline. Source text is loaded and recursively expanded first. The lexer produces tokens, the parser constructs AST nodes, the type checker annotates and validates those nodes while maintaining lexical scopes and ownership facts, and the emitter converts the validated program into a C token buffer. Finally, the runtime prelude, FFI headers, raw C inclusions, and generated tokens are written to the output file. The driver can optionally invoke a host C compiler through the generated runtime process boundary [1].

| Phase | Primary responsibility | Principal functions | Primary result |
|---|---|---|---|
| Source expansion | Resolve `include` and `includec`, record dependencies, detect cycles, and preserve source provenance. | `include_process_line`, `include_expand_handle`, `source_import_fail` | Expanded Basalt source and copied C fragments. |
| Parsing | Convert tokens into expression, type, statement, and program AST nodes. | `ast_type`, `ast_expr`, `ast_expr_prec`, `ast_stmt` | AST node identifiers stored in compiler-managed arrays. |
| Semantic checking | Validate types, ownership consumption, scope visibility, and branch flow joins. | `tc_expr`, `tc_stmt`, `tc_consume_call`, `tc_*scope`, `tc_flow_*` | Validated and annotated AST plus checker state. |
| Collection | Discover declarations, generic specializations, closures, tuples, and dependent generated types before emission. | `gen_collect_expr`, `gen_collect_stmt` | Emission work lists and specialization metadata. |
| C emission | Emit declarations, statements, expressions, match dispatch, cleanup, and runtime support. | `gen_program`, `gen_function`, `gen_stmt`, `gen_match_stmt`, `gen_expr`, `code_emit`, `emit_runtime` | C token buffer and runtime text. |

## Key invariants represented by the graph

The parser and checker are separated from final C emission, but the emitter deliberately consults semantic metadata when it must preserve type-aware behavior. In particular, `gen_expr` uses checked type information for generated calls and value formatting, while `gen_stmt` and `gen_match_stmt` use terminal-flow analysis to avoid emitting cleanup that cannot be reached [1].

The branch-flow functions form a safety boundary around alternative control-flow paths. A baseline is saved before branch analysis, restored before a sibling branch, and merged only after the branch facts are available. This prevents a move performed in one `match` arm from being incorrectly treated as if it had happened in every arm [1].

The defer path is intentionally represented as an emitter stack. `gen_defer_push` records an expression, while `gen_emit_defer_from` replays expressions in reverse order at the required scope boundary. Return expressions are materialized before cleanup by the statement emitter, while the deferred expression itself is evaluated at cleanup time under the current implementation [1].

Recursive include expansion has two distinct output paths. A Basalt module is reopened and passed through `include_expand_handle`, allowing nested Basalt includes to be expanded. An `includec` target is read as raw bytes and copied into the C-source buffer. Both paths record canonicalized dependency edges and reject cycles before continuing [1].

## Limitations and maintenance notes

This graph intentionally omits low-level lexer, symbol-table, type-compatibility, capacity-management, runtime-helper, and platform-specific process functions. Those functions remain part of the implementation but are represented as grouped boundaries where expanding them would make the primary compiler pipeline difficult to read. For a complete call graph, regenerate the graph from the source rather than treating this selected view as exhaustive.

The source contains functions with similar responsibilities at different abstraction levels. For example, `gen_program` orchestrates the complete C token generation pass, whereas `emit_c_file` writes the runtime prelude and flushes both raw C text and generated tokens to disk. The graph therefore distinguishes **token generation** from **file serialization** and does not draw an incorrect `gen_program → emit_runtime` edge [1].
