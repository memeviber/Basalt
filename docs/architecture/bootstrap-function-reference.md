# Bootstrap Basalt Function Reference

## Scope and audit standard

This document is a source-anchored reference for the selected control-plane functions of the Bootstrap Basalt compiler. It covers parser recursion, semantic checking, ownership and control-flow joins, collection, C emission, deferred cleanup, and recursive source expansion. The source of record is [`src/bootstrap/basaltc.basalt`](../../src/bootstrap/basaltc.basalt) [1].

The reference has been normalized so **every function is described with the same fields**. Each profile states the function’s purpose, inputs, return behavior, state mutations and side effects, failure or boundary behavior, selected direct callers, and selected direct callees or external dependencies. This prevents one subsystem from receiving a detailed description while another is reduced to a short label.

The companion artifacts are [`bootstrap-function-graph.mmd`](./bootstrap-function-graph.mmd), [`bootstrap-function-graph.png`](./bootstrap-function-graph.png), and the earlier architecture overview [`bootstrap-source-graph.png`](./bootstrap-source-graph.png). The graph is a selected view rather than a complete 379-function call graph. An edge between two selected functions means that the caller directly invokes the callee in the current Bootstrap source. Calls to functions outside the selected set are named as external dependencies instead of being silently omitted.

> **Coverage rule:** every profile below has the same source anchor plus seven descriptive categories: purpose, inputs, return behavior, state and side effects, failure and boundaries, selected direct callers, and selected direct callees or external dependencies. Self-recursion is explicitly marked rather than hidden.

## Compiler pipeline

The Bootstrap compiler loads and expands source files, tokenizes the resulting source, constructs an AST, checks types and ownership, collects generation dependencies, emits a C token stream, and serializes the runtime plus generated output to a C file. The driver can then invoke a host C compiler through the generated process boundary [1].

| Phase | Responsibility | Selected functions | Output or state produced |
|---|---|---|---|
| Source expansion | Classify ordinary lines, `include`, and `includec`; resolve targets; record dependency edges; reject cycles; preserve source provenance. | `include_process_line`, `include_expand_handle`, `source_import_fail` | Expanded Basalt source and copied raw C source. |
| Parsing | Convert token sequences into expression, type, statement, and nested AST nodes. | `ast_expr`, `ast_expr_prec`, `ast_type`, `ast_stmt` | AST identifiers stored in compiler-managed arrays. |
| Semantic checking | Validate types, ownership consumption, lexical visibility, borrow state, and branch joins. | `tc_expr`, `tc_stmt`, `tc_consume_call`, `tc_enter_scope`, `tc_leave_scope`, `tc_flow_*` | Checked annotations and mutable checker state. |
| Collection | Discover generic instances, closures, tuples, generated types, and dependent declarations before emission. | `gen_collect_expr`, `gen_collect_stmt` | Work lists and generation registries. |
| C emission | Emit declarations, expressions, statements, match dispatch, cleanup, and C tokens. | `gen_program`, `gen_function`, `gen_stmt`, `gen_stmt_terminates`, `gen_match_stmt`, `gen_expr`, `gen_defer_push`, `gen_emit_defer_from`, `gen_emit_all_defers`, `code_emit` | Typed C token buffer plus generation metadata. |
| File serialization and runtime | Write the runtime prelude, FFI headers, raw C source, line directives, and generated tokens. | `emit_runtime` and external `emit_c_file` | Final generated C translation unit. |

## Relationship notation

The caller and callee fields deliberately distinguish three cases. A **selected direct relationship** is a direct call whose other function is documented in this file. An **external dependency** is a direct call to a lower-level or omitted function. An **entry boundary** is a caller outside the selected slice, such as `main`, `pipeline_main`, or `emit_c_file`.

The source anchors below were checked against the current Bootstrap file. Each link points to the function definition line, not to an approximate section heading.

## Cross-cutting invariants

The parser functions return identifiers into compiler-managed arrays rather than heap objects exposed to callers. Negative parser results and zero type-parser results are sentinels; they are not interchangeable and should be interpreted according to the function that produced them [1].

The checker functions return `void` because semantic failure is fatal. Their meaningful outputs are state mutations: type annotations, scope visibility, ownership and borrow facts, generic bindings, and branch-flow snapshots. The flow sequence is baseline save, branch check, successful-branch save, sibling restore, conservative merge, and frame end [1].

The emitter functions also return `void`, but their output channel is different: they append typed tokens or C text to global buffers or an output handle. `code_emit` records source position and epoch metadata for each generated token. `emit_runtime` writes directly to the output file and is therefore called by `emit_c_file`, not by `gen_program` [1].

Deferred cleanup uses a LIFO stack. `gen_defer_push` records an expression identifier without evaluating it. `gen_emit_defer_from` replays the expressions in reverse registration order, and `gen_emit_all_defers` requests replay from the function-level baseline. The current implementation evaluates a deferred expression at cleanup time, so rebinding semantics must be understood from the current scope state [1].

Recursive source expansion has two distinct paths. A Basalt module is reopened and processed recursively, while an `includec` target is copied as raw C source. Both paths canonicalize the target, record the dependency edge, check whether the target reaches the parent, and report fatal import errors through `source_import_fail` [1].

## Audit findings and limitations

The audit found **30 documented function profiles**, all with source anchors matching the current definition lines. The profiles now use the same source anchor plus seven descriptive categories and explicitly distinguish selected relationships from external boundaries. Self-recursive parser, checker, collector, and emitter paths are named in the caller or callee fields rather than being hidden inside a generic phrase such as “recursive helpers.”

This remains a selected graph, not a complete call graph. The Bootstrap source contains 379 functions, including lexer helpers, symbol-table routines, type-compatibility helpers, capacity management, runtime emission helpers, platform-specific process routines, and diagnostic internals. Those omitted functions are named as external dependencies where they directly affect a documented function, but they are not given separate profiles in this file.
